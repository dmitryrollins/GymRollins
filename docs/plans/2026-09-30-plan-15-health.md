# Plan 15: Apple Health + calories per workout

Date: 2026-09-30 · Branch `feat-health` (worktree `wt-health`) · Owner-approved scope (Wave 2).

## Goal

1. **Calories per workout** — an estimate from the 2024 Adult Compendium of Physical Activities, shown on the
   workout Summary, the workout detail in Log and as a weekly total on the Log tab, always labelled
   "≈ 320 kcal (estimated)" with an info sheet (method + citation).
2. **Apple Health** — opt-in (Settings → Apple Health, plus a skippable card on the last onboarding step):
   - write each finished workout as an `HKWorkout` (with the calorie estimate) and every weigh-in logged in the app
     as `bodyMass` / `bodyFatPercentage` samples; edits and deletes in the app update/delete the Health copies;
   - read body weight and body fat % from Health into the Body tab (last 2 years on enable, incremental after).
3. A reusable Health layer (`GymHealth` package) that the future Watch target can link.

## Calories (GymCore, pure)

### Source values (unaltered)
`ios/GymRollins/Resources/met-values.json` holds every Compendium activity the app uses: code, MET and the
Compendium's description, copied verbatim from pacompendium.com (Conditioning Exercise, Running, Bicycling and
Walking headings, fetched 2026-09-30), plus a `source` block (citation, URL, terms). The terms ("free to use for
commercial purposes", "Please do not change MET values", "Please cite…") are quoted in `docs/licenses/compendium.md`;
`CREDITS.md` carries the credit line. An app unit test decodes the bundled JSON and checks every code the
estimator can pick exists with its published MET.

### Formula
`kcal = MET × body weight (kg) × active hours` (1 MET ≈ 1 kcal · kg⁻¹ · h⁻¹, the Compendium's standard
conversion), summed over the workout's activities, rounded to whole kcal.

- **Active time** = `endedAt − startedAt − pausedSeconds` (paused time excluded). No end → no estimate.
  Under 60 s → no estimate. Capped at 4 h (a workout left running overnight can't write thousands of kcal to
  Health); the estimate records that it was capped.
- **Body weight** = the latest weigh-in on or before the workout's start, else the earliest after it, else a
  **70 kg default** (the Compendium's reference adult) — flagged, and the UI says "using 70 kg".
- **Time split** — cardio sets with logged time (`minutes`, or `sec`/60) get exactly that time (scaled down if
  they add up to more than the workout). The rest of the workout is shared between strength entries (and cardio
  entries without logged time) in proportion to their working-set counts. A cardio-only workout's unlogged
  leftover (transitions) is not counted.
- **Effort** (one per workout):
  1. If any working set has RPE or RIR: mean RPE (RIR → RPE = 10 − RIR). ≥ 8.5 vigorous, ≥ 6 moderate, else light.
  2. Otherwise rest density = strength minutes ÷ strength working sets: ≤ 1.5 min/set vigorous, ≤ 4 moderate,
     else light.
  3. No strength sets and no RPE → moderate.

## Apple Health (`ios/Packages/GymHealth`)

Depends on GymCore + GymData only, so a watch target can link it.

- `HealthStore` protocol (async, `Sendable`): availability, authorization request/status, save/delete workout by
  external id, save/delete body samples by external id, anchored body sample changes.
- `HealthKitStore` (iOS/watchOS only): `HKWorkoutBuilder` (begin → add an `activeEnergyBurned` sample with the
  estimate's **active** part, `(MET − 1) × kg × h` — Health counts resting energy separately, so the gross number
  shown in the app would double-count it (Codex round 17; owner can flip this) → metadata → end → finish), `HKMetadataKeyExternalUUID` = our workout/weigh-in id on every sample,
  deletion by that metadata predicate (`deleteObjects(of:predicate:)` only touches this app's own samples),
  `HKAnchoredObjectQueryDescriptor` over bodyMass + bodyFatPercentage (one anchor, archived to `Data`),
  samples whose source bundle id is this app are flagged `fromThisApp`.
- `FakeHealthStore` (actor): in-memory store with the same semantics, used by package tests and the DEBUG
  `-fakeHealth` launch flag (seeded with three Withings weigh-ins).
- `HealthSync` (`@MainActor @Observable`): the logic.
  - **enable()**: request authorization → persist enabled + enabledAt → import → export. **disable()** stops
    syncing (keeps the ledger/anchor; nothing is deleted from Health).
  - **Export (reconcile)**, serialized so two runs never interleave: candidates = app workouts ended after
    enabledAt + everything in the export ledger. For each: gone/deleted → delete from Health; fingerprint
    (start, end, kcal, name, activity) changed → delete by external id, then save; unchanged → skip. Same for
    weigh-ins (app-sourced entries dated after enabledAt − 24 h). Deleting by external id before every save makes
    exports idempotent even if the ledger is lost (reinstall). Failures leave the ledger untouched → retried on the
    next run; the Summary shows "Couldn't save to Apple Health".
  - **Import**: anchored query from now − 2 years (signed in: only after weigh-ins were pulled from the cloud at
    least once). Skip `fromThisApp`; a bodyMass sample → a weigh-in (source `appleHealth`) that stores the sample's
    UUID in `healthSampleId` (synced), edit time = the sample's date (so a newer cloud deletion wins). Skipped when
    any row — live or a tombstone, from any device — already has that sample id, or when a non-Health entry on the
    same calendar day is within 0.1 kg (same weigh-in typed by hand); values outside `DomainLimits` skipped. Body fat
    attaches to the imported weigh-in within ±10 min (`healthFatSampleId`); an early body fat sample waits up to 2
    days for its weight. Deletions in Health (applied first in each batch) delete the weigh-in or clear its body fat.
    The new anchor is saved only after the batch is applied.
  - Triggers: enable, every local data change (`dataChanged`), remote changes from Supabase sync, app foreground.
- **Source on weigh-ins**: `BodyweightEntry.source` (`app` | `appleHealth`) plus `healthSampleId` /
  `healthFatSampleId`, stored on `BodyweightRecord` and synced as nullable `bodyweight.source`,
  `health_sample_id`, `health_fat_sample_id` columns (migration `20260930000002_bodyweight_source.sql`), so another
  device knows an entry came from Health, never exports it back, and dedupes / deletes it by sample id. Health-imported rows sync like manual ones.
- **Permissions**: share = workouts, active energy, body mass, body fat %; read = body mass, body fat %.
  Purpose strings `NSHealthShareUsageDescription` / `NSHealthUpdateUsageDescription`. Settings shows per-type
  write status (HealthKit never reveals read status: we say so), "Partially allowed" / "Not allowed" states and an
  "Open Settings" button. `HKHealthStore.isHealthDataAvailable() == false` → the row says "Not available on this
  device" and nothing is called.
- Entitlement `com.apple.developer.healthkit` in `project.yml` (no `healthkit.access`: clinical records need Apple approval); signing untouched. The team's provisioning profile must gain the HealthKit capability (Xcode with the owner's Apple ID signed in registers it on the next device build).

## UI

- Summary: a full-width kcal tile ("≈ 320 kcal", "estimated", ⓘ) + Health line ("Saved to Apple Health" /
  "Couldn't save to Apple Health"). Workout detail: the same tile. Log: "≈ 1,240 kcal this week (estimated)" under
  the week strip. ⓘ → `CalorieInfoSheet` (formula, effort rule, body weight used, citation).
- Settings → Apple Health: toggle, availability, permission rows, last import count, "Open Settings".
- Body tab: imported weigh-ins show "Apple Health".
- Onboarding (Connect Claude step): an "Apple Health (optional)" card with "Connect Apple Health".
