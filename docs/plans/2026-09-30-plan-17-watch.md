# Plan 17: Apple Watch companion (log sets + rest timer from the wrist)

Date: 2026-09-30 · Branch `feat-watch` (worktree `wt-watch`) · Owner-approved scope (Wave 2).

## Hard constraint

The owner's watch is an **Apple Watch Series 5 on watchOS 10.6.1** (it can't run watchOS 11+). The watch app's
deployment target is **watchOS 10.0**: standard watchOS 10 SwiftUI only (`NavigationStack`, `TabView`
`.verticalPage`, `digitalCrownRotation`), no watchOS 26 APIs, no Liquid Glass on the watch. Swift 6 strict
concurrency applies. Code the watch links compiles for watchOS 10; iOS-only code is behind `#if os(iOS)`.

## Goal

1. **Phone ↔ watch sync (WatchConnectivity).** The phone stays the source of truth (SwiftData only on the phone).
   While a workout runs on the phone the watch shows it live: exercise, "Set 3/5 · 135 lb × 8" (next planned set,
   user's unit), rest countdown, workout clock, heart rate. Watch actions: **Log set** (planned values, Digital Crown
   adjusts weight/reps first, stepping by the phone's plate/dumbbell increment), **+30s**, **Skip rest**,
   **previous/next exercise**, and **Start today's workout** (phone must be reachable).
2. **Rest timer on the watch** with a haptic at 0, alive with the wrist down thanks to an `HKWorkoutSession`.
3. **HealthKit on the watch**: `HKWorkoutSession` + `HKLiveWorkoutBuilder` (traditional strength training) for the
   phone workout's duration — heart rate and active energy — saved to Health at the end, with **exactly one** Health
   workout per GymRollins workout (see "Single Health workout").
4. Complications: **skipped** (optional in scope; a watchOS 10 WidgetKit complication needs an App Group + widget
   extension + its own signing — not trivial). Documented as a follow-up.

## Architecture

```
ios/Packages/GymWatchLink      (Foundation only; iOS 26 · macOS 26 · watchOS 10)
  WatchMessages.swift          WatchState (phone→watch), WatchCommand (watch→phone), envelope coding, version
  WatchCommandLedger.swift     remembers applied command ids (sendMessage + transferUserInfo duplicates)
  CrownStepper.swift           weight/reps stepping on the loadable grid, in the user's unit
  WatchHealthRules.swift       who writes the Health workout (phone vs watch), sync identifiers/metadata keys
  WatchWorkoutModel.swift      the watch's view model (state, crown edits, actions, reachability) — testable on macOS
  WatchConnectivityLink.swift  WCSession wrapper shared by both sides (#if os(iOS) || os(watchOS))
ios/GymRollins/Features/Watch  (phone)
  WatchStateMapper.swift       session/profile/library → WatchState (reuses WorkoutActivityContent)
  WatchSyncController.swift    observes the env, pushes state, receives commands, launches the watch workout
  AppEnvironment+Watch.swift   applies commands through WorkoutSession.perform (same path as the Live Activity)
  FakeWatchTransport.swift     DEBUG `-fakeWatch`: in-memory transport + a probe/inject button for UI tests
ios/GymRollinsWatch            (watchOS 10 app, bundle id com.rollins.gymrollins.watchkitapp, WKApplication)
  GymRollinsWatchApp.swift     app + WKApplicationDelegate (handles the phone's startWatchApp workout config)
  WorkoutRecorder.swift        HKWorkoutSession + HKLiveWorkoutBuilder, heart rate, save/discard at the end
  Views/*                      Idle / Workout (set + crown, rest, controls) pages
```

Phone-side action handling reuses `WorkoutActivityAction` + `WorkoutSession.perform(_:exercise:)` (the Live Activity
path): a new `.logSet(… weightKg:reps:)` case shares `.logPlannedSet`'s guards (same workout, not finished, set is
still the entry's next set, reps-based exercise), and `.showExercise(workoutId:fromEntryId:direction:)` moves the
shown exercise only when the watch was looking at the phone's current target entry. Rest actions carry the rest's
`startedAt` the watch saw, so a queued +30s / Skip never lands on a later rest.

### Messages (versioned, Codable)

Every WatchConnectivity payload is `["v": 1, "type": "state"|"command", "data": <JSON>]`. A payload with a newer
major version is ignored (logged). `WatchState` goes phone→watch via `updateApplicationContext` (latest wins) plus an
immediate `sendMessage` when reachable; `WatchCommand` goes watch→phone via `sendMessage` (reachable) with a
`transferUserInfo` fallback (queued, delivered once). Each command has its own `id`; the phone's ledger (persisted,
last 200) drops a command it already applied. Start-today is `sendMessage`-only: unreachable → "Open GymRollins on
iPhone".

### Single Health workout (dedupe)

- When the watch's `HKWorkoutSession` is running for phone workout W, the watch sends `healthClaim(W)`.
- The phone **accepts** the claim only while W is the running workout and Apple Health is on in the app; it records
  it in `HealthSyncState.watchClaims[W]` and the next `WatchState` says `watchRecordsHealth = true`.
- Phone exporter (`HealthSync.exportWorkouts`): a workout recorded by the watch (ledger value `watch`) is complete —
  never exported, re-exported or edited in Health by the phone. A claimed workout that the watch hasn't confirmed is
  skipped until `WatchHealthRules.phoneFallbackDelay` (2 h) after it ended; after that the phone first looks in
  Health (`HealthStore.workoutCopies`, read access to workouts) for the watch's copy of W (its external id, synced to
  the phone's Health store). Copies are told apart by `GymRollinsWriter` metadata (`watch` / `phone`; older copies by
  recording device), never by HealthKit source — a companion watch app's samples may carry the iOS app's source. Found: ledger `watch`, never exported. Not found (or no read
  access): the phone exports its estimate. A failed lookup skips W for that run.
- Watch at the end: saves its workout **only** if the final state says the claim was accepted and it is still within
  `WatchHealthRules.watchSaveWindow` (1 h, strictly inside the phone's fallback); otherwise it discards it. After a
  save it sends `healthRecorded(W, avg/max HR)`; the phone marks the ledger `watch` — however late it arrives, as
  long as the phone hasn't written W itself (idempotent).
- Confirmation after the phone wrote W (review fix): kept in `HealthSyncState.watchAcks`; each export run looks for
  the watch's copy and, once Health shows it, deletes only the phone's own copy (the workout objects classified as the
  phone's, one by one — `HealthStore.deleteOwnWorkout`) and marks the ledger `watch`: one copy, the measured one. If the watch's
  copy never shows up within `HealthSync.watchAckWindow` (24 h) — e.g. HealthKit replaced it with the phone's newer
  version under the shared sync identifier — the phone's copy stays. Nothing is ever deleted without W's id, and the
  only copy is never deleted.
- Defense in depth: the watch's workout uses the same `HKMetadataKeyExternalUUID` and sync identifier
  (`gymrollins.workout.<id>`) the phone's exporter uses.

## Tests (TDD)

- GymWatchLink (`swift test`, macOS): message round trips + unknown-version rejection; ledger dedupe/bounds; crown
  stepping (lb barbell grid with 45 lb bar offset, kg, dumbbells, clamp at 0, reps); Health rules; watch model
  (actions carry ids, crown edits reset on a new set, unreachable start message, rest countdown + haptic trigger).
- GymHealth: claimed workout not exported; recorded-by-watch never exported; fallback export after the delay.
- App unit: state mapping (session → WatchState), action application through `WorkoutSession` (stale/duplicate
  ignored, adjusted weight logged, rest actions tied to the rest they saw, exercise navigation), claim acceptance.
- App UI (`-fakeWatch`): inject the watch's "Log set" and see the set logged on the logging screen.
- Builds: watch target for `generic/platform=watchOS Simulator` and `generic/platform=watchOS`
  (`CODE_SIGNING_ALLOWED=NO`). No watchOS simulator runtime is installed, so on-watch behaviour (HealthKit session,
  haptics, crown) needs a real watch — see the report.
